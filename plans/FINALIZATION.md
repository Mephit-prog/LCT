# План финализации кода wineid

Цель — довести существующую реализацию до воспроизводимого, ограниченного по ресурсам release candidate, **не добавляя новые модели и экспериментальные алгоритмы**. Готовность кода и подтверждённое качество распознавания — два разных результата: без независимого GT и калибровки основной API продолжает возвращать кандидатов и отказы, а не автоматически принятый slug.

План составлен по текущей рабочей копии ветки `lora-jina-synthetic_2`, базовый коммит `d78809b`, включая незакоммиченные изменения OCR/fusion. Старый backlog и продуктовые gates: [STATUS.md](STATUS.md). Устройство fusion: [candidate_source_blend.md](candidate_source_blend.md). Локальный OCR: [local_russian_ocr_implementation.md](local_russian_ocr_implementation.md).

## 1. Проверенная исходная точка

- Обычный offline suite: **208 passed, 6 skipped, 30 warnings**. Тяжёлые smoke-тесты были явно отключены; внешние OCR-вызовы и загрузка весов не выполнялись.
- `python3 -m compileall -q wineid tests` — успешно.
- `python3 -m pyflakes wineid tests` — **8 замечаний**: неиспользуемые импорты в `api.py`, `server.py`, `fusion_policy.py`, `test_ocr_eval.py`, `test_warm_ocr.py` и переменная `pid` в последнем файле.
- Найден конфликт установки: `requirements.txt` требует `Pillow>=10,<12`, а `constraints.txt` закрепляет `Pillow==12.3.0`. Прохождение тестов в существующем окружении не доказывает установку с нуля.
- Уже реализованы локальные OCR-адаптеры, warm Paddle IPC, manifests, online fusion, versioned policy, ограничения отдельных запросов и тесты отказов. Их не нужно писать заново.
- Общий жёсткий deadline, эквивалентность offline/online решения, чистая установка и совместная нагрузка API+OCR+CLIP пока не подтверждены. Независимого отчёта о качестве на полевых фото нет.

## 2. Зафиксировать границы первого релиза

Предлагаемый минимальный профиль, который нужно утвердить до работ:

1. **FastAPI — основной сервер**, `wineid/server.py` — совместимость с legacy/eval. Общая бизнес-логика, без двух независимых реализаций распознавания.
2. Один API-процесс, один выбранный локальный OCR-провайдер, ограниченное выполнение CLIP. Несколько uvicorn workers не входят в поддерживаемый профиль, пока нет общего управления ресурсами.
3. Выбрать **один** реально проверенный OCR-профиль на целевом сервере: warm Paddle либо Tesseract. MinerU/PDF и поддержка всех CPU/GPU комбинаций не блокируют этот релиз.
4. Jina включается только с согласованными весами, class index и лицензией. Photo→photo — только с verified gallery; её отсутствие не блокирует OCR/photo→text.
5. Сохранить разделение: основной API — policy/отказ; `/v1/eval/predict` — forced top-1. Catalog fallback без evidence остаётся явно отмеченным в диагностике и не считается распознаванием.
6. Не менять молча дефолт `WINE_ROI_MODE=refuse`. Mistral — только явный opt-in, не автоматический fallback. TTA, conditional OCR и эвристические признаки — выключены в релизном профиле до отдельной проверки.

## 3. Последовательность PR

### PR-01 · P0 — чистая установка и обязательный CI

**Файлы:** `requirements*.txt`, `constraints.txt`, конфигурация CI, перечисленные выше файлы с lint-замечаниями.

- Устранить конфликт Pillow, выбрать и проверить поддерживаемую версию Python и совместимые зависимости. Не просто скопировать `pip freeze` из смешанного conda/user-site окружения.
- Добавить воспроизводимые dev-зависимости и offline job: `pytest`, `compileall`, `pyflakes`. Тяжёлые модели и OCR canary — отдельные opt-in jobs.
- Закрыть 8 lint-замечаний; убрать устаревающее использование `Image.fromarray(..., mode=...)` там, где режим выводится из массива.
- Сохранить согласованный `fuzzywuzzy`: не добавлять `python-Levenshtein` только ради удаления warning, поскольку это может изменить scoring. Зафиксировать реально используемый backend.
- Включить новые OCR/fusion-модули и тесты в будущие PR; не полагаться на untracked-файлы или локальный `artifacts/`.

**Приёмка:** установка в пустое изолированное окружение, зелёные тесты и статические проверки; у каждого skip есть причина. Обычный CI работает без ключей, скачивания моделей и внешнего OCR.

### PR-02 · P0 — единая конфигурация, запуск и fingerprint policy

**Файлы:** `api.py`, `server.py`, `pipeline.py`, `text_policy.py`, `fusion_policy.py`, `ocr.py`; предлагаемые новые `config.py` / `runtime.py`.

- Вынести дублирующуюся сборку catalog → aliases → OCR → vision → blender → pipeline из двух `main()` в общий bootstrap.
- Валидировать конфигурацию до загрузки моделей: конечные положительные timeouts, лимиты, совместимость provider/mode, наличие файлов и согласованность версий. Ошибка конфигурации — отказ запуска, не тихая деградация.
- Управлять ресурсами через lifecycle/context manager: startup, canary, shutdown и очистка при частичном сбое запуска. `atexit` оставить страховкой, а не единственным механизмом.
- Расширить fingerprint до полного профиля принятия решения: aliases, правила OCR-нормализации, provider/версии/веса, preprocessing/ROI, conditional OCR и его параметры, candidate budget, scoring/код конфигурации.
- Сейчас `Pipeline.fusion_config` не содержит `conditional_ocr`, а текстовая policy привязана только к CSV/backend/blend. Устранить возможность применить policy после изменения влияющей на решение настройки.
- Проверять request-level `roi_mode`/bbox против разрешённого калиброванного профиля. Некалиброванный режим не должен автоматически выдавать `accepted` только потому, что startup-проверка policy прошла.
- Версионировать изменение схемы; legacy policy без полного provenance не разрешать в релизном acceptance-профиле.

**Приёмка:** оба сервера получают одинаковую конфигурацию; несовместимый артефакт отклоняется до обслуживания запросов. Тесты мутаций каждого значимого параметра подтверждают несовместимость policy. После неудачного startup не остаются процессы/дескрипторы.

### PR-03 · P0 — одинаковое решение offline и online

**Файлы:** `pipeline.py`, `fusion_run.py`, `fusion_eval.py`, `fusion_compare.py`, `fusion_policy.py`, `blend.py`.

**Наблюдаемые расхождения:** `fusion_eval.evaluate()` создаёт `Blender` без runtime aliases и вызывает `policy.decide()` без дополнительной проверки prompt collisions из `Pipeline`. В `fusion_run` визуальная ветка использует полный кадр даже при ручном bbox, тогда как online использует crop. `--ocr live` в harness сейчас создаёт только Mistral, хотя online поддерживает локальные движки.

- Выделить общие операции получения evidence, ранжирования и acceptance; offline и HTTP должны использовать их с одной конфигурацией. Offline-диагностика может сохранять больше данных, но не менять алгоритм незаметно.
- Передавать aliases, crop/TTA, OCR-профиль, collision metadata и полный fingerprint в evaluator. Добавить явную загрузку policy для финальной оценки acceptance.
- Подключить выбранный локальный OCR к `fusion_run` через общий factory/lifecycle. Режимы `manual_oracle`, local, external и none сохранять раздельно.
- Проверять связь evidence с SHA изображения, каталогом, индексами и конфигурацией; совпадения одного `query_id` недостаточно. Для test проверять policy и отсутствие утечек из calibration/gallery.
- Добавить parity-регрессии: одинаковые bytes/bbox/config дают одинаковые evidence, Top-K, status и accepted slug через offline, Pipeline и HTTP. Покрыть aliases, одинаковые class prompts, no_text, отказ источника, singleton и deadline.
- В отчёте разделить ranking и acceptance; явно учитывать ambiguous, пропавшие источники и ошибки. Recall пула считать до/после расширения серий и ограничения бюджета, не исключая неудачные запросы.

**Приёмка:** offline-метрики относятся именно к выпускаемому online-пути. Подменённые evidence/config отклоняются; synthetic/manual/candidate-link диагностика не превращается в independent accuracy.

### PR-04 · P0 — общий deadline и ограничение вычислений

**Файлы:** `fusion_vision.py`, `pipeline.py`, `warm_ocr.py`, `local_ocr.py`, `ocr.py`, общий runtime.

- Убрать неограниченное синхронное выполнение CLIP из HTTP threadpool: использовать ограниченный долгоживущий процесс/executor с возможностью завершить зависший worker и восстановить его. Не загружать веса заново на каждый запрос.
- Сохранить один monotonic deadline от начала upload до ответа; учесть очередь, decode, OCR/CLIP, поиск, сериализацию и ограниченный резерв на завершение worker.
- Проверить warm/cold OCR не только на чтении IPC: `_verify()` хеширует файлы при перезапуске, `_stop()`/`wait()` добавляют время после timeout. Долгую проверку/перезагрузку вынести из короткого request budget; восстанавливаться в фоне с `not_ready/busy` и ограничением повторов.
- Разделить typed-причины `capacity_exceeded`, timeout, crash/OOM, несовместимые артефакты. Сейчас визуальный `RuntimeError` сворачивается в общий `vision_unavailable`.
- Ограничить совокупную нагрузку OCR+CLIP на одном CPU/GPU. Process-local semaphore не объявлять глобальным лимитом между несколькими API-процессами.
- Если Mistral остаётся поддерживаемым online-профилем, обеспечить общий timeout и лимит ответа, а не только таймауты отдельных HTTP-операций; иначе явно оставить его вне гарантируемого SLA.

**Приёмка:** fake-worker, зависающий навсегда, не удерживает HTTP-запрос и слот бесконечно; ответ укладывается в бюджет с заранее определённым небольшим допуском. Проверены crash/restart, отсутствие дочерних процессов после остановки, восстановление следующего запроса. `asyncio.wait_for` вокруг неотменяемого потока само по себе не закрывает задачу.

### PR-05 · P0 — admission control, HTTP-контракт и readiness

**Файлы:** `api.py`, `server.py`, `tests/test_api.py`, `tests/test_http_negative.py`, `tests/test_warm_ocr.py`, `API.md`.

- Ограничивать число принимаемых upload **до** чтения тела. Сейчас FastAPI `BoundedBody` буферизует POST до endpoint-auth и semaphore распознавания: лимит одного тела не ограничивает суммарную память множества соединений.
- Проверять авторизацию до дорогого парсинга; задать лимиты multipart-полей, размера текстового запроса, соединений и очереди. Согласовать лимиты приложения и reverse proxy.
- Проверить slow/chunked upload, disconnect, malformed multipart, decompression bomb и повторные перегрузки. Слоты освобождаются на любом выходе.
- Зафиксировать таблицу HTTP-кодов и reason codes для обоих адаптеров, включая ошибки eval. Изменения legacy-контракта делать явно; не отдавать внутренние исключения или содержимое входа в error response.
- Разделить liveness, catalog readiness, доступность распознавания и наличие acceptance policy. Не использовать legacy `/ready`, означающий готовность каталога, как единственную проверку готовности распознавания.
- После canary учитывать crash/unresponsive worker. Текущий warm readiness проверяет только живой процесс; canary использует `WINE 2024`, а cold canary допускает `no_text`. Добавить проверку русского текста/цифр на фиксированной разрешённой fixture.

**Приёмка:** под перегрузкой — предсказуемый `503 busy`, а не неограниченный рост памяти/очереди. Health доступен и отражает отказ модели. Контрактные тесты подтверждают неизменность основного refusal и отдельного forced eval.

### PR-06 · P1 — воспроизводимый release bundle

**Файлы:** отдельные locks API/CLIP/OCR, manifests, `LICENSES.md`, конфигурация контейнера либо сервиса, пример окружения без секретов.

- На выбранном целевом сервере закрепить совместимые Python/torch/transformers/Paddle, системные библиотеки и один OpenMP runtime. Не переносить macOS workaround из [REAL_RUN.md](REAL_RUN.md) в универсальную инструкцию.
- Подготовить одну поддерживаемую схему развёртывания; раздельные окружения OCR и API допустимы на том же сервере. Задать лимиты CPU/RAM/VRAM, приватный IPC, права на temp и read-only модели.
- Собрать manifest выпуска: git revision, lock/image digest, CSV/aliases, base weights и remote-code revisions, adapter, class index, optional verified gallery, OCR weights и policy с SHA-256.
- Обеспечить получение артефактов из согласованного хранилища и проверку checksum. Не требовать локальных `/Users/...` путей и не считать full-vision checkpoint доступным.
- Установку/скачивание выполнять при подготовке, не на пользовательском запросе. Проверить реальный запуск с запрещённым egress.
- Закрыть лицензии реально выбранных компонентов и транзитивного HF-кода; секреты не включать в образ, git, manifests или логи.

**Приёмка:** на чистой машине из инструкции собирается тот же профиль; отсутствующие/изменённые веса дают понятный startup failure. Предыдущий согласованный bundle доступен для rollback.

### PR-07 · P1 — реальные smoke, наблюдаемость и нагрузка

**Файлы:** opt-in integration suite, нагрузочный сценарий, runtime/API instrumentation, отчёт целевого сервера.

- Выполнить настоящие Cyrillic OCR и Jina smoke с закреплёнными весами; проверить HTTP → ROI → OCR/CLIP → fusion без подмены движков mock-объектами.
- Добавить request ID, версии профиля, время upload/очереди/этапов/total, счётчики отказов, busy, timeout, worker restart и отсутствие evidence. Не логировать фото, OCR-текст, data URI и Authorization.
- Измерить cold/warm p50/p95/p99, throughput, peak RSS/VRAM и количество процессов/дескрипторов совместно для API+OCR+CLIP.
- Проверить штатную и избыточную конкурентность, большие входы, зависание/падение worker, восстановление, shutdown, недоступные артефакты и нехватку места в temp.
- Согласовать целевые нагрузку, p95 и допустимую долю ошибок **до** приёмочного прогона. Не объявлять последовательный CPU inference серверным SLA.

**Приёмка:** сохранены команды, версии, нагрузочный профиль и отчёт; нет накопления процессов, очереди или temp-файлов. Сквозной бюджет подтверждён на заявленной нагрузке. Smoke доказывает исполнение, но не точность SKU.

## 4. Порядок и зависимости

`PR-01 → PR-02 → PR-03 → PR-04/PR-05 → PR-06 → PR-07 → PR-08`.

Подготовку целевого окружения и лицензий из PR-06 можно начинать параллельно PR-02. PR-04 и PR-05 можно разделить между разработчиками после фиксации общего runtime-контракта. Разметка данных идёт параллельно с самого начала. Сроки фиксировать после выбора платформы/провайдера; получение GT, лицензий и весов не включать в оценку только кодовых правок.

**Первая практическая итерация:** исправить dependency conflict и lint, включить CI, затем закрыть fingerprint и offline/online parity. До этого не подбирать production-пороги по текущему evaluator.

## 5. Отдельный gate качества — не заменяется завершением PR

Соответствует B01/B02/B08/B09/B10 из [STATUS.md](STATUS.md):

1. Согласовать единицу ответа, accepted precision, coverage, unknown false accepts, latency и правила неоднозначности; назначить владельцев данных и выпуска.
2. Подготовить независимые реальные known/unknown/ambiguous фото, provenance и splits по съёмкам/duplicate families до настройки. Кандидатные CSV↔uploads связи не повышать до verified автоматически.
3. На одном validation сравнить выбранный локальный OCR, frozen/LoRA и простой fusion. Image→image включать только при verified gallery. Ручные ROI/транскрипции — отдельная диагностическая абляция.
4. Настроить acceptance только на validation через тот же путь решения, что используется online; сохранить полный policy fingerprint и freeze.
5. Один раз оценить untouched test: ranking, accepted precision/coverage, unknown false accepts, ошибки похожих SKU, знаменатели и интервалы неопределённости.
6. Только при выполнении согласованных gates — ограниченный pilot/shadow и затем решение о выпуске. При провале оставить candidates-only/отказы; не ослаблять пороги ради демонстрации.

## 6. Definition of Done

**Код завершён / RC:**

- [ ] Чистая установка и обязательный CI проходят; все skips объяснены.
- [ ] Online/offline parity и fingerprint конфигурации покрыты регрессиями.
- [ ] Нет неявной отправки фото наружу, скрытого mock или acceptance без совместимой policy.
- [ ] Upload, inference, очередь и recovery имеют проверенные ресурсные лимиты/deadline.
- [ ] Реальные OCR/CLIP smoke и совместная нагрузка пройдены на целевом сервере.
- [ ] Release manifest, права использования, инструкция запуска и rollback готовы.

**Пользовательское распознавание готово:** дополнительно пройден независимый gate качества и утверждён пилот. **Production:** дополнительно эксплуатационная защита, мониторинг и проверенный откат под нагрузкой.

Не включать в финализацию: новое обучение/full-vision, CAM/GrabCut, ANN, PDF/MinerU API, внешний ETL, обучаемый reranker и расширение числа поддерживаемых платформ. Возвращаться к ним только по измеренной проблеме после RC.
