# 03. OCR pipeline на общем сервере

## Область и текущий статус

**Целевая схема — один сервер, на котором работают API, ROI, OCR, поиск и опциональный Jina CLIP.** Отдельный OCR-хост, облачный OCR и GPU не являются обязательными условиями. Характеристики сервера пока не зафиксированы: выбирать устройства, версии и конкуренцию после инвентаризации именно целевой машины, а не по характеристикам локального компьютера разработчика.

В `wineid/ocr.py` есть общий `OCRResult` и явный выбор `WINE_OCR_PROVIDER=none|tesseract|paddle|mineru|mistral` (mock — только явный тестовый opt-in). Cold Paddle/MinerU в `local_ocr.py` по-прежнему стартуют отдельным процессом на запрос — это только эксперимент. Добавлен `WINE_OCR_MODE=warm` для Paddle: один локальный IPC worker с прогретыми весами, canary при старте, без очереди, с ограниченным вводом/выводом, deadline/kill+restart. Его manifest проверяет SHA-256 всех файлов и версии окружения. Это не измерение реального inference на целевом сервере: готовность к эксплуатации и latency ещё требуют проверки.

Основной кандидат для этикеток — PaddleOCR PP-OCRv5 `ru`, Tesseract `rus+eng` — CPU baseline и возможный самостоятельный профиль после замеров. MinerU/PDF — отдельная необязательная документная задача, не зависимость распознавания вина. Mistral — только явно разрешённый внешний эксперимент, не основной путь и не автоматический fallback. Подробности окружений и этапов: [local_russian_ocr_implementation.md](local_russian_ocr_implementation.md).

## 1. Проверка сервера и выбор одного online-профиля

1. Зафиксировать ОС/архитектуру, Python, CPU/доступную RAM, свободный диск; при наличии NVIDIA — GPU/VRAM/драйвер и совместимость конкретной сборки Paddle. Измерить ресурсы уже работающих API, индекса и CLIP. Не предполагать, что вся память и GPU свободны для OCR.
2. Изолировать зависимости OCR в venv/container **на том же сервере**; API не должен устанавливать все тяжёлые движки. Закрепить версии пакетов, модели, SHA-256 весов и лицензии. Веса загрузить при подготовке релиза; прогрев выполнить при старте процесса на целевом устройстве. На запросах не скачивать модели.
3. Сначала проверить Tesseract и Paddle на разрешённой синтетической кириллице, затем на одинаковых размеченных ROI с русским и латинским текстом. Выбрать один online-движок по качеству, warm/cold latency и ресурсам **вместе с CLIP**, а не запускать все движки на каждом фото.
4. В production явно задать `WINE_OCR_PROVIDER`: незаданная переменная теперь равна `none` (ключ Mistral сам по себе не включает отправку); mock требует `WINE_OCR_PROVIDER=mock WINE_ENABLE_MOCK_OCR=1` и допустим только в тестах.

## 2. Контракт ROI → OCR → поиск

**Вход:** один цветной ручной/автоматический front ROI из [плана 02](02_label_segmentation.md), `roi_id` и оставшийся общий deadline. При `WINE_ROI_MODE=refuse` без bbox OCR не вызывается; наличие CLIP может обеспечить отдельную визуальную ветку, но не создаёт OCR ROI. Ручной bbox поддержан в `/api/recognize`; legacy stdlib endpoint принимает только изображение.

**Выход:** существующий `OCRResult`: `roi_id`, `status`, `raw_text`, `normalized_text`, `model`, `latency_ms`, `error_code`; boxes/confidence остаются `null`, пока нет проверенного источника этих данных. Текущие строки `model` локальных адаптеров не идентифицируют точные веса: до выпуска добавить версионированный manifest runtime/моделей и связать его с отчётами.

- MIME проверять по содержимому, ограничить bytes/pixels/crop, учитывать EXIF; передавать очищенный RGB crop без исходных метаданных. Невалидное изображение отклонять до запуска движка.
- Сохранять исходный OCR-текст в результате; поисковую нормализацию версионировать отдельно. `ё/е`, транслитерация, очистка импортёрского текста — поисковые преобразования, не исправление raw OCR. Не подменять текст ближайшим названием каталога и не считать любое четырёхзначное число годом.
- `no_text` — успешное исполнение без пригодного текста; `timeout` и `provider_error` — отдельные ошибки, не пустой успех. Отсутствие CLI, сбой процесса, превышение output, невалидный ответ и busy имеют reason codes без утечки stderr/текста клиенту. Warm worker при старте fails closed на отсутствии/несовпадении manifest; OOM отражается как сбой worker (без точной диагностики типа сбоя).
- Raw/normalized текст сохранять в закрытых offline-артефактах только по разрешённой политике хранения. В production-логи не писать изображения, OCR-текст, data URI и секреты.

## 3. Исполнение и общий бюджет ресурсов

Первый технический canary допустим на subprocess baseline. Для online Paddle теперь реализован один долгоживущий worker с локальным IPC через private pipes, без публичного OCR-порта. Не считать его нагрузочно проверенным профилем: несколько HTTP процессов создадут независимые worker и не разделяют общий GPU admission control.

- Начать с одного API-процесса и одного OCR worker, затем менять конкуренцию по нагрузочным измерениям. Не создавать копии CLIP и OCR на каждый uvicorn worker. Текущий `Pipeline.ocr_slots` — локальный семафор на экземпляр, не общий лимит сервера; `WINE_MAX_WORKERS` ограничивает HTTP, а не GPU.
- При совместной GPU обеспечить общий admission control для OCR и CLIP либо использовать измеренный профиль CPU OCR + GPU CLIP. Ограничить CPU threads, RAM, VRAM и temp-диск с запасом для API/декодирования. Обучение, OCR каталога и тяжёлые batch/PDF не запускать одновременно с online без выделенного бюджета.
- Очередь OCR в warm режиме нулевой длины: конкурентный запрос получает `busy`; API возвращает HTTP `503 busy`, если нет другой пригодной ветки. При визуальном сигнале бленд может продолжать без OCR. Общего лимита между несколькими процессами API пока нет.
- Один monotonic deadline включает upload/ROI, очередь, CLIP, OCR, поиск и сериализацию; клиент eval ждёт 10 с, текущий HTTP timeout по умолчанию 8.5 с. OCR получает **остаток**, не новый полный timeout. В текущем blend сначала выполняется vision, затем OCR: не обещать параллелизм или весь бюджет OCR. Проверить wall-clock пределы реальной обработкой, а не только проверкой времени после inference.
- Timeout локального OCR прекращает всю process group; warm worker перезапускается на следующем запросе с canary в оставшееся время. Output и ввод ограничены уже во время чтения; temp cold subprocess удаляется по завершении запроса. Уборка temp после аварийного завершения API, контроль всех CPU/GPU ресурсов и принудительное прерывание произвольного vision inference ещё не закрыты.
- Без автоматической цепочки Paddle → Tesseract → Mistral и без online retry в первом релизе. Дополнительный движок/crop допустим только после доказанного выигрыша и проверки remaining deadline.

## 4. Последовательность работ

1. **Инвентаризация и canary:** manifest сервера/окружения, реальные исполнения Tesseract/Paddle, ошибки отсутствующих моделей/CLI, измерения cold start и ресурсов. CLI/языки выбранных версий подтвердить исполнением.
2. **Тёплый локальный worker:** lifecycle/startup/shutdown, bounded queue, общий лимит ресурсов с CLIP, deadline/cancel/kill+restart, ограниченный output и temp cleanup. Сохранить интерфейс `OCRResult`.
3. **Интеграция:** явный provider, проверка модели и прогрева в readiness, startup fails closed при неверной конфигурации. Разделить catalog-ready, OCR-ready и готовность распознавания; нынешний `/ready` проверяет в основном конфигурацию, не реальный inference. Не менять ROI/acceptance policy ради успешного OCR.
4. **Оценка и нагрузка:** одинаковые независимые ROI → каждый кандидат OCR → поиск; затем полный запрос с ROI/CLIP при целевой конкуренции. Зафиксировать выбранный профиль и численные критерии выпуска до финального test.
5. **Деплой:** supervisor/systemd или containers на одном сервере, restart/backoff, health probes, TLS/auth и upload/rate limits на публичном API, внутренний worker без внешнего доступа. Закреплённые веса read-only, временные файлы с квотой/TTL, запрет сетевых загрузок после подготовки. Откат — совместимый комплект кода, окружения, весов, индексов и policy.

## 5. Проверки и приёмка

- Unit/contract: Unicode, пустой текст, неверный ввод, отсутствующий движок/веса, падение процесса, timeout и прекращение потомков; отсутствие текста/секретов в логах. Реальные модельные integration-тесты запускать opt-in на сервере, не подменять mock.
- Независимые разрешённые фото с буквальными транскрипциями и split по съёмкам: CER/WER с правилами нормализации, ошибки названий/цифр, доля пригодного текста, text Recall@K относительно ручной транскрипции. Сбои входят в общий знаменатель. Три неразмеченных фото `eval/` — не GT.
- Нагрузка всего сервера: cold/warm p50/p95/p99 end-to-end и OCR, длина/время очереди, timeout/error rate, peak RSS/VRAM, CPU/GPU utilization. Проверить параллельные запросы с CLIP, OOM, рестарт worker, отсутствие весов, заполнение диска и cleanup. Допустимая конкуренция определяется этими измерениями, а не числом HTTP workers.
- MVP готов, когда выбранный **один** локальный OCR работает на целевом сервере без скачиваний на запросе, ошибки не маскируются, общий deadline/лимиты подтверждены нагрузкой, есть воспроизводимый отчёт по качеству. Установка всех трёх движков и PDF API не обязательны.
- Успешный OCR не доказывает точный SKU: принятие slug остаётся задачей калиброванной text/fusion policy и gates [STATUS.md](STATUS.md). OCR эталонов — только offline для verified gallery; дополнительные ROI, extraction и документный pipeline — отдельные измеряемые улучшения.
