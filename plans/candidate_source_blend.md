# Единый план: blend источников → серия → точный slug

Реальный локальный прогон с pinned Jina + LoRA и снимками uploads/eval, воспроизведение, парные **диагностические** результаты и незакрытые gates: [REAL_RUN.md](REAL_RUN.md). Offline harness `wineid.fusion_run`/`fusion_compare` не превращает кандидатные ссылки на uploads в ground truth; acceptance не калибровалась.

Объединяет план независимых источников и gates выпуска с разбором «как смешивать сигналы, чтобы выдавать один точный slug». Цель ТЗ — 90–100% exact-slug совпадений и надёжное выделение top-1; это целевой показатель, не подтверждённое качество. Большой численный margin сам по себе не доказывает правильность.

**Статус: базовая интеграция реализована и выполнен локальный прогон на реальных байтах, качество и advanced-этапы не подтверждены.** `wineid/blend.py`, `fusion_vision.py`, `fusion_policy.py`, `fusion_eval.py`, `fusion_run.py`, `fusion_compare.py`, `pipeline.py`, `api.py` и `server.py`: union, RRF/global-gap, расширение серий, OCR-признаки, версия артефактов и forced top-1 для оценки. Без реальных размеченных фото/verified gallery нет калиброванной production policy и заявленных 90–100%. TTA (`WINE_QUERY_VIEWS=3`) и fixed-seed multi-view verified gallery (`clip_eval build --synthetic-views`) есть как отключённые по умолчанию эксперименты. Отложены локальные точки, HSV, обучаемый reranker, production SLA и реальная калибровка unknown. Не путать с лексическим `wineid/search.py:BLEND_VERSION = search-blend-v1` (внутреннее ранжирование **одного** текстового источника). Базовая рабочая ветка — `lora-jina-synthetic_2`, с дообученной Jina CLIP; `main` здесь содержит только предшествующий backend, а `origin/lct-release` — более поздний коммит с тем же full-vision экспериментом. Не переносить решения в `main` без отдельного merge.

## Источники кандидатов (каждый с независимым статусом)

1. **OCR→текстовый индекс**: `wineid/ocr.py` + `wineid/search.py` (Top-K `wine_id`/slug, score, rank, OCR raw/status, версия каталога); описание подключения ключа — [mistral_ocr_service.md](mistral_ocr_service.md). Ошибка/пустой OCR означает *нет сигнала*, а не нулевую вероятность у всех SKU.
2. **Фото→канонический текст SKU через дообученный Jina CLIP**: загрузить LoRA через `load_adapter` поверх pinned Jina, применить одинаковый препроцессинг ко всем query; сравнить с baseline frozen и full-vision только при наличии его checkpoint. Сохранить `checkpoint_sha256`, revision, preprocessing, prompt, crop и версию класса. Пока CLI/offline, не live ветка API.
3. **Фото→фото** по *ручной verified* gallery (если появится): `wineid/visual.py` / `clip_eval.py`; агрегировать несколько референсов на SKU без преимущества за их количество. Не использовать автоматически совпавшие имена файлов как GT; если проверенной gallery нет — источник отключён, OCR и photo→text не блокируются.
4. Проверенные каталожные поля/алиасы — объяснение и контроль конфликтов (сорт/год/производитель), **не** независимый обученный сигнал. Источник внешних фото/маркетплейсов — только после проверки media relation, права и provenance.

## 1. Основания и ограничения анализа

По предоставленному анализу каталога (числа нужно воспроизвести отдельным versioned отчётом):

- 2103 SKU, 1749 названий, 135 производителей; 158 серий / 351 SKU (16,7%). Серия — `(canonical_normalize(producer), name_tokens(name))`; 70 групп / 154 SKU имеют буквально одинаковые название и производителя.
- Среди 240 пар одной серии различаются сладостью/стилем 106 (44%), сортом 79 (33%), цветом 47 (20%), годом 33 (14%); только крепостью — 24 (10%), только другими словами названия — 20 (8%), без найденных различий — 14 (6%). Категории частично пересекаются.
- В 126 парах с привязанными фото 32% имеют pHash distance ≤10. Это сходство изображений, **не доказательство**, что различить их можно только текстом; привязки ещё требуют проверки.
- Cosine текстовых Jina-эмбеддингов внутри серии: медиана 0,993; у 90% пар ≥0,95. Это мотивирует проверку гипотезы «картинка выбирает серию, OCR — её участника», но не доказывает её для image→image.
- 1375 привязанных packshot'ов в train manifest — не 1375 verified референсов. SKU без фото должны оставаться доступны через OCR и photo→text.

Исходное состояние до интеграции: `Index._blend` содержит неподобранные веса и query-relative evidence; в `clip_eval.rank` смесь `score/100` и `(cos+1)/2` подавляла маленькие визуальные отрывы (в эксперименте заменена на global-gap; старая visual policy несовместима). `pipeline.decide` без policy по-прежнему отказывается в основном API, но `/v1/eval/predict` теперь запрашивает forced top-1. Онлайн-CLIP включается только явно настроенным совместимым index/encoder.

## 2. Общий контракт и генерация кандидатов

Ввести `CandidateEvidence`: `wine_id`/slug, source, rank, **сырой** score и его тип/диапазон, ROI, ссылка на OCR raw/clean, статус/причина отсутствия сигнала, catalog/index version, checkpoint SHA и preprocessing/prompt version. Проверять конечность score, валидность ID и совместимость версий. Дубли одного SKU внутри источника агрегировать до fusion; разные slug и урожаи не сливать.

Пул — **union top-K** OCR→text, photo→text и, при наличии verified gallery, photo→photo. Начальный K=20–50 на источник — гиперпараметр. Затем добавить всех участников найденных серий из каталога: иначе OCR не сможет выбрать отсутствующего в top-K участника. Зафиксировать общий бюджет, правило обрезки и измерять recall до/после обрезки и расширения.

Галерею считать **офлайн**, при старте загружать готовые L2-нормированные векторы и manifest. Несколько фото агрегировать на уровне SKU без бонуса за количество (фиксированный бюджет видов; max/mean сравнить на val). Query и gallery — одинаковая версия encoder/checkpoint/preprocessing. Ошибка одного источника не блокирует остальные; отсутствие всей evidence — отдельный результат, не уверенный ответ.

## 3. Baseline fusion и правильная шкала

1. **RRF:** `S(c) = Σ w_i / (k + rank_i(c))`, ранги с 1, старт `k=60`; отсутствующий кандидат не получает вклад этого источника. Это baseline без калибровки шкал, но не вероятность.
2. **Gap fusion:** `g_i(c) = (s_i(c) − max s_i) / τ_i`. τ — одна положительная константа на источник для всех запросов; старт `τ_img=0.05`, `τ_txt=10`, веса `w_img=1`, `w_txt=0.7`, `w_clip=0.3` — только начало подбора. Photo→text требует собственной τ.
3. **Не использовать z-score по top-K запроса:** он превращает маленькие различия внутри серии в сильный сигнал. Упоминание «cosine → z-score» в исходном списке приоритетов заменено на global-gap. Вычитание max само по себе не меняет порядок линейной суммы; относительную силу задают `w_i/τ_i`, их нельзя интерпретировать как независимо определённые параметры.
4. Различать missing: источник упал/не запущен; SKU не имеет референса; SKU вне top-K. Нельзя автоматически считать все эти случаи худшим cosine. Где возможно, пересчитать доступные сигналы на union; иначе хранить mask и явно валидировать missing policy. Для отсутствующего источника вклад 0; для отсутствующего фото — нейтральный вклад с mask, а не штраф за отсутствие данных. Эффект на SKU без фото проверить отдельно.

Сравнивать RRF и gap fusion на одном пуле. Не считать OCR и картинку статистически независимыми: оба используют одну этикетку.

## 4. Главный эксперимент: серия → участник

### Нормализация и признаки

`clean_ocr` применять **до** поиска и извлечения признаков, сохраняя raw text. В смешанных кириллических словах исправлять латинские гомоглифы и `0→о`, в числоподобных токенах — `O→0`; настоящую латиницу (`Blanc`, `Merlot`) и буквенно-цифровые названия не портить. Ограничить преобразования контекстом и покрыть тестами.

Три состояния каждого признака: match / conflict / unknown. Не прочитан на фото **или отсутствует у кандидата** → 0. Мягкие стартовые бонусы в единицах итогового gap-score (не z-score):

| Признак | Match | Conflict | Ограничение |
|---|---:|---:|---|
| Год | +1,5 | −2,0 | 19xx/20xx, учитывать несколько дат и год основания |
| Сладость/стиль | +1,0 | −1,5 | Длинные формы раньше коротких; экстра брют ≠ брют |
| Сорт | +0,7 | −0,7 | Нормализованный словарь каталога, границы слов, купажи |
| Цвет | +0,5 | −1,0 | «Белое», а не «Кокур белый»; цвет этикетки не равен цвету вина |
| Крепость | +0,5 | −0,5 | 5–25%, допуск ±0,25; не путать 100% и крепость |
| Производитель | +0,5 | −1,0 | Проверенные алиасы, а не подстрока |

Крепость из хвоста slug — эвристика, не поле GT: использовать только после аудита схемы суффиксов и проверки диапазона, исключить годы/номера дублей. Набросок `slug_alcohol` без этих проверок в production не переносить. В текущем `BlendConfig` эвристика **выключена по умолчанию** (`use_slug_alcohol=false`); opt-in пригоден только для отдельной диагностики и меняет fingerprint конфигурации. Неоднозначное OCR-наблюдение не превращать в уверенный конфликт.

### Два уровня

- Индексировать `family_key` по нормализованному производителю (с проверенными алиасами) и `name_tokens(name)`. Это эвристика группировки, а не GT идентичности; проверить ложные слияния/разбиения. Разные slug остаются отдельными кандидатами.
- **Уровень 1:** `F(f) = max_{c∈f} Σ_i w_i g_i(c)` — максимум совместной оценки участника, без преимущества большой серии. Сравнить с flat fusion. Жёсткий выбор одной серии может потерять правильный SKU, поэтому отдельно проверить rerank нескольких лучших серий.
- **Уровень 2:** внутри выбранной серии `M(c) = attribute_bonus(c) + ε_img·g_img(c) + ε_txt·g_txt(c)`. Старт `ε_img=0.2`; остаточный текстовый сигнал сохранять для различающих слов, не покрытых регулярками. Веса подбирать, не объявлять признаки безошибочными.
- Для multi-family варианта явно определить общую оценку `F(f)+M(c)`: в нём признаки могут изменить серию-победителя. Не выдавать такой алгоритм за жёсткий «сначала выбрать одну серию». В исходном наброске реализован именно multi-family вариант.
- Канонический представитель — только deterministic tie-break при отсутствии различающей evidence, не замена информативного ранжирования: предпочесть slug без **подтверждённого** duplicate-суффикса `-1/-2`, затем verified фото, затем алфавит. Это не гарантирует exact-slug GT. Проверить алиасы `golubitskoe-estate` / `pomeste-golubitskoe` и уточнить у организаторов правила дублей.

## 5. Две политики ответа и калибровка

**Оценка `/v1/eval/predict`:** для валидного изображения и доступного каталога возвращать лучший slug независимо от acceptance policy. Forced top-1 не означает «уверенно распознано». Это отдельный режим ранжирования, а не выключение отказов основного API. Проверить также ROI default `refuse`: одной замены nullable slug недостаточно, нужен действующий путь получения кандидатов. Если OCR пуст/упал, использовать доступный визуальный источник; если все источники недоступны, контракт технической ошибки должен быть явным. При требовании slug даже без evidence согласовать и логировать детерминированный catalog fallback; не маскировать его как распознавание. Ошибки файла, авторизации и пустой каталог не подменять случайным slug.

**Основной `/api/recognize` и `/v1/recognize`:** сохранить существующий контракт, acceptance policy и `ambiguous`/отказ при недостатке данных. Без проверенной policy автоматический accepted slug не включать. При unknown показывать похожие варианты, по возможности из разных серий, не нарушая схему ответа.

`softmax(S/T)` с T, подобранной по log-loss на val, даёт лишь условное распределение **внутри заданного пула**. `p_top1`, `p_top5` и margin не доказывают, что GT вообще в пуле/каталоге; при пяти кандидатах `p_top5=1` тривиально. До проверки калибровки не называть их вероятностью правильного ответа. Для unknown нужны реальные негативы, абсолютные scores, качество OCR, согласие источников и отдельная acceptance policy. Softmax только внутри выигравшей серии не измеряет уверенность выбора серии.

Хранить raw-score margin и calibrated confidence раздельно. Проверять reliability/log-loss, accepted precision/coverage и unknown false accepts; нельзя достигать «заметного отрыва» простым уменьшением T. Policy version включает catalog fingerprint, family/alias rules, candidate budget, checkpoints, prompt/crop, OCR provider/model, scoring code и missing policy.

## 6. Валидация без смешения уровней доказательства

**Разработка:** разрешить подбор стартовых весов на синтетической validation — 184 вина от held-out производителей (`artifacts/tz/wines.csv`), 3–5 `augment.field_view` с фиксированными seed, отличными от обучения. Не использовать те же данные как независимый test; если на этом split уже выбирали checkpoint, явно отметить зависимость и получить новый holdout. Галерея — отдельные verified референсы, query не включать в неё как референс.

Synthetic OCR из канонического текста с шумом годится для unit/logic checks и предварительного перебора, но раскрывает поля, которых на этикетке может не быть. Отдельно оценивать настоящий OCR на изображениях (локальный PaddleOCR/EasyOCR либо согласованный Mistral). Не смешивать эти результаты в одну метрику.

**Gate выпуска:** независимые реальные known/unknown/ambiguous фото с похожими SKU, split по съёмкам/производителям/duplicate families до настройки. Пилот 30–50 фото полезен для диагностики, но недостаточен для гарантии 90–100%. На real validation настроить acceptance и OCR gating; затем freeze и один untouched test. Три `eval/` фото — только smoke test, не подбор весов.

Матрица на одних query: OCR-only, frozen photo→text, LoRA, full-vision (если checkpoint доступен), verified photo→photo, union, RRF, gap, hierarchy; затем ablation clean_ocr / attributes / family expansion / conditional OCR. Отчёт:

- exact-slug acc@1/@5, Recall@K union до/после budget, family_acc@1;
- member_acc@1 при правильной серии, отдельно для multi-SKU серий;
- ошибки near-duplicate, known без фото, missing каждого источника;
- распределения margin для верных/неверных, accepted precision/coverage, unknown false accepts;
- paired helped/harmed, знаменатели и неопределённость, p50/p95 latency и стоимость.

Ручные OCR-примеры с реальными cosine из пользовательского разбора (включая «100 оттенков Саперави» и «Гордиенко Пино Нуар») превратить в регрессионные фикстуры, если доступны исходные данные. Это проверка логики, не accuracy и не калиброванные p=0,69 или margin=0,54.

## 7. SLA и отложенные улучшения

После baseline с always-on OCR проверить условный запуск: маленький визуальный отрыв, низкий абсолютный score или несколько участников конкурентной серии. Проверять размер серии по каталогу, не только наличие двух участников в top-K. Доля серий 16,7% каталога не означает такую же долю OCR-вызовов; экономию и потерю accuracy измерять на запросах. Cold start и warm p95 считать отдельно, все источники под общим deadline; SLA 3 с пока цель, не гарантия.

По очереди, только с ablation:

1. Адаптивные веса по длине/качеству OCR, blur и согласию top-1; согласие не гарантирует правильность.
2. Query TTA (полный кадр, этикетка, центр) и 3–5 fixed-seed gallery views; max/mean сравнить. Несколько бутылок требуют выбора целевой ROI, max по всем кропам может смешать их признаки.
3. ORB/SIFT или SuperPoint+LightGlue + RANSAC на top-5, inliers как дополнительный сигнал; HSV — слабый признак, не жёсткий фильтр.
4. Logistic/LightGBM reranker с gap/rank/missing, атрибутами, family size, качеством OCR и inliers, hard negatives той же серии; группировать обучение по query, исключить утечки производителей.
5. AQE/k-reciprocal — поздний эксперимент: усреднение соседей может ухудшить различение участников серии.

Обновления каталога: инкрементально пересчитывать документы, family index и verified gallery для новых SKU без переобучения; атомарно переключать согласованные версии и проверять применимость policy.

## 8. Порядок работ и критерии готовности

Оценки времени — ориентир для прототипа, без разметки, скачивания весов и проверки лицензий.

| Приоритет | Работа | Оценка | Проверяемый результат |
|---|---|---|---|
| P0 | Evidence-контракт, split/fixtures и два режима API | 0,5–1 день | Forced top-1 не зависит от acceptance; основной API сохраняет отказы; ошибки явны |
| P1 | LoRA photo→text онлайн; verified gallery и photo→photo при доступности | 1–2 ч после подготовки данных | Версии совместимы, missing не блокирует остальные источники |
| P2 | Union + family expansion + RRF | 1–2 ч | Recall@K и OCR-only/visual-only/RRF на одних query |
| P3 | clean_ocr, признаки, gap и hierarchy | 2–4 ч | Регрессии гомоглифов, годов, сладости, сортов, unknown и дублей |
| P4 | Synthetic harness и перебор, затем real validation | 2–3 ч на harness | Воспроизводимый отчёт/ablation, веса и policy versioned |
| P5 | Калибровка и conditional OCR | 1–2 ч на прототип | Precision/coverage, unknown FAR, качество против always-on OCR, p95 |
| P6 | TTA и multi-vector | 1–2 ч | Улучшение на holdout с учётом ресурсов |
| P7 | Локальные признаки | 0,5–1 день | Paired helped/harmed на близких этикетках |
| P8 | Обучаемый reranker | 1 день после данных | Выигрыш над простым fusion на untouched test |

**Обязательные тесты:** пустой пул/каталог; один кандидат; все источники missing; неизвестный slug; NaN score; τ/T≤0; дубли рангов; SKU без фото; участник серии вне исходного top-K; одинаковые оценки и детерминированность; неизвестный атрибут без штрафа; латиница без повреждений; несколько дат/купаж; timeout OCR; несовместимые manifests; eval forced top-1 при production ambiguous. Обновить `API.md` при реализации поведения endpoint, не менять HTTP-контракт молча.

**Первый измеримый результат:** воспроизводимая сравнительная таблица источников, union и fusion с provenance, missing, near-duplicate ошибками и затратами. Синтетика разрешает продолжать эксперименты, но ни она, ни наличие checkpoint не открывают gate production-выпуска.
