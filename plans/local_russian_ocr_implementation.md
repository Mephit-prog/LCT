# План развёртывания локального OCR на общем сервере wineid

**Контур:** один существующий сервер для API, ROI, поиска, CLIP и OCR, а не отдельный OCR-хост. Основной online-план и границы MVP — [03_ocr_pipeline.md](03_ocr_pipeline.md). Ниже — детали окружений и необязательный документный трек; PDF/MinerU не блокируют выпуск OCR этикеток.

**Задачи раздельны:** (1) OCR русского текста на ROI винных этикеток для `wineid`, (2) разбор PDF/страниц, в том числе таблиц. Первый релиз НЕ обещает точный slug или качество PDF только потому, что OCR запустился. Основной стек: PaddleOCR PP-OCRv5 `ru` на изображениях; MinerU **pipeline** + `cyrillic` для документов; Tesseract `rus+eng` — дешёвый CPU baseline/fallback, Mistral — отдельно включаемый внешний сравнительный провайдер, не неявный fallback. VLM MinerU не включать в RU baseline.

## 0. Реальный статус кода и измерений

- В `wineid/ocr.py` есть `OCRResult`, `MistralOCR`, `MockOCR`; `wineid/pipeline.py` управляет ROI, deadline и поиском. Без `WINE_OCR_PROVIDER` используется `none`, внешний вызов и mock не активируются по наличию ключа/текста. Cold Paddle/MinerU по-прежнему создают новый process на запрос; добавлен отдельный warm Paddle worker (`WINE_OCR_MODE=warm`) через приватные pipes с реальным canary, manifest весов, bounded I/O и kill+restart по deadline. CPU Tesseract стартует per-request; readiness требует реального canary. MinerU CLI вызывается с `-b pipeline -m ocr -l cyrillic`, подаёт один PNG ROI и читает один `.md`. PDF API/CLI и структурированный JSON MinerU **не реализованы**.
- Tesseract 5.5.1 c `rus+eng` проверен на синтетическом «Привет, мир! Саперави 2024»: точный текст, около 68 мс для малого изображения через stdin. Три неразмеченных фото дали неоднородный результат (одно читаемо, одно шумное, одно пустое); это не CER/WER. PaddleOCR 3.7.0 / paddlepaddle 3.3.1 на macOS arm64 удалось установить, но прежняя попытка исполнения модели не вернула результат после аппаратного сбоя. MinerU с реальными весами НЕ запускался. Контрактные тесты с mock не доказывают, что CLI и веса работают на сервере.
- Ключ Mistral подтверждал авторизацию, но `/v1/ocr` ответил 429 на три модели; причина неизвестна. Ключ из переписки перевыпустить, не помещать в код/CI. Старые версии OCR не использовать. Оплата/доступ/условия хранения проверяются до отдельного opt-in canary.
- В проекте нет размеченных PDF и проверенных транскрипций пользовательских фото. Нет оснований объявлять качество или готовность к production.

## 1. Платформа и сетевой контур

**GPU-профиль (если GPU доступен):** сначала зафиксировать ОС/архитектуру, CPU/RAM/disk, GPU/VRAM и потребление уже работающих API/CLIP на общем сервере. Для Linux/NVIDIA подобрать поддерживаемый драйвер/CUDA *под конкретные версии Paddle/MinerU*. Бюджет OCR считать по свободным ресурсам с резервом для остальных компонентов; требования отдельного OCR-хоста не переносить на весь сервис. Проверить совместимость по официальным install guides, `nvidia-smi`, `paddle.is_compiled_with_cuda()` и inference canary до выбора образа. Не считать GPU-вариант автоматически быстрее на коротких ROI из-за cold start/очереди.

**CPU-профиль:** проверить на фактических ресурсах общего сервера (в том числе CPU OCR вместе с GPU CLIP); лимитировать `OMP_NUM_THREADS`, `MKL_NUM_THREADS`, OpenBLAS и число воркеров после измерения, чтобы не переподписать ядра. Вес и задержку MinerU pipeline на CPU проверить отдельно, прежде чем обещать 10-секундный SLA. Ориентиры — не формальные минимальные требования: фиксировать peak RSS/VRAM и p95 именно на целевом оборудовании.

Логически разделить FastAPI (публичный через reverse proxy, аутентификация, upload limits), OCR worker (loopback/Unix socket/IPC на том же сервере), read-only версионированные веса и временные файлы с TTL. Отдельные процессы/venv/container не означают отдельные машины. API, CLIP и OCR используют общий бюджет CPU/RAM/GPU; начинать с одного API-процесса и одного OCR worker, не размножать веса через uvicorn workers. Для общей GPU нужен общий admission control либо измеренный CPU-профиль OCR. Никаких публичных портов worker, root-привилегий, отправки изображений вовне без opt-in. HTTPS/reverse proxy, токен/ACL, лимиты размера и скорости, секреты в secret manager; логи — ID запроса, engine/version, status/latency без Authorization, OCR-текста, изображений и data URI. Установить квоты на GPU/CPU/RAM/disk, sandbox temp и egress policy (после подготовки весов запретить сетевые скачивания).

## 2. Пинование окружений и весов

1. Подготовить два независимых image/venv: `ocr-paddle` и `ocr-mineru` (версии могут конфликтовать); отдельно лёгкий `tesseract` с pinned `rus`/`eng` traineddata. Основное `requirements-api.txt` не превращать в установку GPU/Paddle для каждого пользователя. Выбрать совместимые версии Linux Python/Paddle/PaddleOCR/MinerU/CUDA по upstream документации, записать lock, образ digest, SHA-256 весов, зеркало скачивания, условия лицензии кода **и весов** до использования в закрытом продукте. Текущие локальные 3.7.0/3.3.1 — не доказанная серверная конфигурация.
2. При подготовке релиза (не на запросе) загрузить веса; при старте worker на целевом устройстве загрузить их в память и прогреть до readiness. Отдельный smoke на PNG с кириллицей для Paddle `lang=ru`, `ocr_version=PP-OCRv5`; MinerU pipeline с `-l cyrillic` проверить на PNG и PDF на **выбранной закреплённой версии CLI**. Зафиксировать фактические ID detector/recognizer и контрольные суммы. Если установленная MinerU использует иные флаги/языковой код, скорректировать worker и тесты до деплоя, а не маскировать ошибку пустым OCR.
3. Подтвердить лицензии MinerU и поставляемых весов по конкретным версиям (в том числе обязательства AGPL, если применимо); PaddleOCR/Tesseract и их веса проверить отдельно. Если юридически нельзя использовать MinerU, это явный блокер его production-развёртывания, но не PaddleOCR.

## 3. Данные и честный бенчмарк

- Для сервиса: независимые реальные фото known/unknown/ambiguous, ручные фронтальные ROI и буквальная транскрипция с названием/годом/производителем; группировать split по съёмке/производителю, не использовать `eval/queries` как GT. Для документов: минимум 20–50 разрешённых страниц PDF (скан, две колонки, таблица, формулы), GT текст и отдельно разметка структуры таблиц. Хранить SHA входа, источник прав, размер, язык, split; не публиковать персональные страницы.
- Одинаковые изображения/страницы и preprocessing для PP-OCRv5, MinerU pipeline, Tesseract; Mistral с подтверждённым доступным model ID — только с разрешением и доступом; версию не предполагать по названию плана. Рендер PDF в фиксированном DPI с ограничением страниц/пикселей, EXIF/alpha/MIME проверять через `roi.py`; сравнивать ручной bbox, затем автоматический ROI отдельно. Не смешивать качество этикетки и документа.
- Отчёт: raw/normalized OCR, CER/WER с указанными правилами Unicode/пробелов/`ё`, доля no_text/ошибок, ключевые поля/цифры, порядок чтения и таблицы, Recall@K поиска, cold/warm p50/p95/peak RSS/VRAM, доля timeout, стоимость. Ошибки входят в знаменатель; синтетический smoke — только тест исполнения. Подбирать на validation, один финальный запуск на untouched test; не заявлять «лучший для русского» по чужому CJK/EN бенчмарку.

## 4. Завершение серверной реализации (последовательность PR)

1. **PR-A: проверка контрактов на сервере.** Прогнать текущие три адаптера с реальными весами и фикстурами на целевой ОС, тестировать отсутствие модели/CLI, 429 Mistral, языковую конфигурацию, нестандартные расширения, ошибка процесса, пустой `.md`, Unicode, timeout и прекращение потомков. Тесты `tests/test_local_ocr.py` сегодня проверяют только интерфейс и mock; добавить отдельный opt-in integration suite без внешнего Mistral в обычном CI. Не маркировать бэкенд `ready` только потому, что сконструирован объект Python.
2. **PR-B: тёплые воркеры.** Заменить per-request Paddle/MinerU subprocess на ограниченный независимый пул долгоживущих процессов по одному набору весов/устройству; выделить GPU affinity, очередь с max size, cancel/deadline/kill+restart зависшего воркера, защиту от OOM, бэкпрешер `503 busy`. Один запрос → один ROI → один текст; не выполнять GPU-инференс синхронно в uvicorn worker. OCR adapter реализует тот же `OCRResult`, сохраняет raw текст, статус `no_text|timeout|provider_error`, model/version; сравнение latency с per-request baseline обязательно. Не запускать GPU-пул в каждом из N HTTP workers.
3. **PR-C: документный endpoint/CLI отдельно от этикетки.** Принимать PDF и изображения, асинхронное задание с ID/TTL/ограничением страниц и повторов; MinerU pipeline возвращает markdown + структурированные блоки/таблицы и page indices, если они действительно доступны у закреплённой версии. Никакой синхронной обработки многостраничного PDF в `/api/recognize` (его контракт — одно фото/ROI и короткий deadline). Описать формат выхода, приватность и политику удаления temp/output. PP-OCRv5 напрямую — baseline для распечатанных страниц; формулы/таблицы не выдавать за достоверную структуру без разметки.
4. **PR-D: интеграция/гейт.** `WINE_OCR_PROVIDER` настроен явно; readiness проверяет реальный ping тёплого воркера и конкретной версии весов, не только наличие объекта; startup fails closed при неверной конфигурации. `WINE_ROI_MODE=refuse` не менять без проверки ROI и отдельного решения. Политика slug/CLIP — отдельная от OCR, существующий отказ сохранить. В `API.md` добавить команды развертывания, конфиг, health, security и rollback; хранить образ/веса/пороговую policy версионированно.
5. **PR-E: нагрузка и эксплуатация.** Прогон N параллельных фото и больших PDF, p50/p95/p99 включая очередь, RAM/VRAM и GPU-util, timeouts, краш процесса, остановка/перезапуск, модель отсутствует, диск заполнен, пакетное удаление temp, недоступность внешнего API. Алерты на долю OCR failures, очередь, OOM, p95; canary/shadow с ручной оценкой, откат по версии образа и весов. Лишь после независимого test и acceptance policy — production пилот.

## Минимальная настройка текущего экспериментального сервиса

`WINE_OCR_PROVIDER=tesseract|paddle|mineru|mistral|none`; `WINE_OCR_MODE=warm` + `WINE_PADDLE_DET_DIR` / `WINE_PADDLE_REC_DIR` / `WINE_OCR_MANIFEST` для долгоживущего Paddle. `WINE_OCR_PYTHON=/path/to/ocr-venv/bin/python` для Paddle/MinerU, `WINE_TESSERACT=/path/to/tesseract`, `WINE_TESSDATA_DIR=/path/to/tessdata`; для Mistral — `MISTRAL_API_KEY` только в secrets. В выбранном Python-окружении должен быть доступен импорт `wineid` и соответствующий пакет; MinerU CLI должен находиться рядом с `python`. Для запроса без ручного bbox при дефолтном `WINE_ROI_MODE=refuse` OCR не вызывается. В режиме `mineru` на сегодняшний день принимается лишь PNG crop этикетки, **не** PDF. Явный provider `none` не включает внешние вызовы даже при наличии ключа. Пока не выполнены PR-A/PR-B и тесты на целевом сервере, `paddle` и `mineru` — экспериментальные адаптеры, не production-ready.

## Критерии приёмки

- Для online MVP выбран один локальный провайдер с реальным inference на **целевом общем сервере**, фиксированными версиями и без скачивания на запросе; ошибки не выдаются за пустой успешный ответ. GPU и CPU профили тестировать отдельно только если оба заявлены поддерживаемыми. Все три движка не являются обязательным условием выпуска.
- Выбранный профиль (тёплый worker для Paddle) выдерживает согласованную нагрузку совместно с API/CLIP и общий deadline, OOM/timeout без утечек очереди/процессов; секреты/PII не логируются. Измерены суммарные RAM/VRAM и задержки, а не только изолированный OCR.
- Есть независимая оценка OCR этикеток и влияния на поиск, сведения о лицензиях; нет обещания точного SKU только по включённому OCR. Gates B01–B10 из [STATUS.md](STATUS.md) остаются обязательными.
- PR-C и PDF/MinerU — отдельный необязательный релиз со своими annotated страницами, метриками и ресурсными лимитами. Длинные PDF/offline jobs не должны вытеснять online OCR/CLIP; при отсутствии ресурсов выполнять их вне online-нагрузки.
