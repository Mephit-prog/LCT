# План распознавания винных этикеток

Проект — **работающий исследовательский прототип, не готовый сервис распознавания**. Есть код, 45 проходящих тестов и сохранённые артефакты реального Jina CPU inference; независимой размеченной validation/test-выборки и подтверждённых метрик качества нет. **Актуальные статусы, единый backlog и gates выпуска — в [STATUS.md](STATUS.md)**. Подробные инженерные правила — в [00_contracts.md](00_contracts.md); остальные документы описывают методы и этапы.

**Дополнение к задаче:** реализован отдельный [zero-shot text↔image путь на Jina CLIP v2](../JINA_CLIP.md), без обязательного OCR и эталонных фото для классификации. [План улучшения ROI-статистик и обогащения сведений о сортах и бутылках](jina_clip_roi_catalog_enrichment.md) учитывает диагностические ошибки этого пути. Ниже — прежний план OCR/image-to-image baseline, а не обязательная последовательность для нового поиска по русскому запросу.

## Что известно

- `strapi_output0709.csv` — принятый GT для каталога (поля `Slug`, `Название вина`, `Винодельня`, `Название фото`): 4 147 строк, из них 2 103 уникальных `Slug`; 2 044 строки — точные повторы. Контрольная сумма CSV: `12a1b0b620db7a2264b094446861e83940a927708d65a1b7ccffda7ec3aeffee`.
- `prod-svoe-vino-strapi/prod-svoe-vino/strapi/uploads/`: 15 803 файлов, в том числе производные и другие типы медиа. Точное совпадение `Название фото` с basename: 0/2 090. По новой консервативной процедуре `wineid.catalog_media` 1699/2103 slug имеют **кандидатную** однозначную группу и единственный original, 404 unresolved; включая 1350 совпадений по фото+slug, 289 только по имени фото, 60 только по slug. Предыдущие 1673/2090 относились к иному эвристическому подсчёту ссылок и не сопоставимы напрямую. **Ни одна такая byte-level связь не считается проверенной автоматически**; `Название фото` встречается у нескольких SKU. Аудит: `artifacts/csv-media-links.jsonl` / `artifacts/csv-media-links-summary.json`.
- `eval/`: три неразмеченных query, два `.jpg` фактически WEBP; клиент ограничен `curl --max-time 10`. Контрольная сумма `eval/queries.tsv`: `3088fed2c7e421d919b31d6fe118ca9243f0ec0a8f9f047c1cfd255dab3dce1b`. Это тест интерфейса, **не validation-набор**.

## Ближайший критический путь

1. Зафиксировать продуктовый сценарий, единицу ответа и критерии качества/отказа; назначить ответственных за GT и выпуск.
2. Собрать независимый пилот с known/unknown/ambiguous, ручными ROI/текстом на диагностической части и split по съёмкам до настройки.
3. Провести photo→SKU evaluation на независимом GT с готовым evaluator, завершить аудит утечек между ветками, добавить provenance текстовой policy и зафиксировать разрешённое окружение.
4. На одном validation сравнить native/padding/manual ROI, name/name-producer и OCR baseline; не смешивать метрики текст→фото и фото→SKU.
5. Выбрать один путь, заморозить конфигурацию и policy, оценить untouched test; только затем интегрировать в HTTP и измерить бюджет/нагрузку.

Подробная приёмка — B01–B10 в [STATUS.md](STATUS.md). Jina CLI сейчас **не подключён к HTTP**; HTTP по умолчанию отказывается от автоматического распознавания.

## Методы OCR/image-to-image baseline (не последовательность обязательной реализации)

1. [EDA](01_eda.md): дедупликация CSV, вручную проверенная небольшая gallery и независимые размеченные пользовательские фото с train/validation/test split. Без этих данных качество нельзя обоснованно оценить.
2. [ROI](02_label_segmentation.md): ручные crop/bbox для первого baseline; автоматическая локализация — только после замера её необходимости.
3. [OCR](03_ocr_pipeline.md): один проверенный вызов Mistral на ROI; raw text, ошибки и deadline. На время разработки — mock и ручные транскрипции.
4. [Поиск](04_text_retrieval.md): простые документы по полям идентичности, FuzzyWuzzy → явный Levenshtein, Top-K; измерить recall до усложнения.
5. [CLIP](05_clip_verification.md): frozen image-to-image rerank по проверенным эталонам, сравнить с text-only; если выигрыша нет — не включать в первую версию. Не угадывать точный slug по визуально одинаковым урожаям.
6. [Интеграция](06_integration_evaluation.md): API, общий deadline, отказ при недостатке информации, сквозной отчёт на независимых фото. Каждый этап можно начать на ручных фикстурах, но production-качество они не доказывают.

**Минимальный сквозной эксперимент до обучения моделей:** ручной ROI → OCR → поиск → `slug` или отказ. Сначала сравнить с ручной транскрипцией и посчитать ошибки OCR/поиска; затем подключать автоматизацию по одной части. Текстовый baseline может работать и без изображений каталога. Эталонные фото нужны для image-to-image CLIP, но не для zero-shot сравнения фото с текстовыми классами; отсутствие полной gallery не блокирует оценку text-only.

## Что не блокирует MVP

- [Обучаемая сегментация](02_label_segmentation.md), OCR эталонов, дополнительные ROI/retry, сложные scoring features, сложные вероятностные калибраторы, visual-global fallback и fine-tuning: только если независимая validation показывает конкретную проблему и улучшение окупает стоимость и задержку.
- Доменные [профили вкуса и состава](01_eda.md) — отдельная аналитическая задача, не признак идентичности этикетки.
- [CLIP + GradCAM + GrabCut и признаки формы](additional_label_segmentation.md) — исследовательская альтернатива локализации, **не шаг 07 обязательного пайплайна**.

Для выдачи подтверждённого slug необходима проверенная на независимой validation политика принятия/отказа; она не относится к необязательным улучшениям.

Не задавать production-пороги точности по трём фото `eval/`. До первого независимого test зафиксировать правила выбора моделей и отказа; при малом числе примеров публиковать знаменатели и неопределённость, а не объявлять достигнутые гарантии.
